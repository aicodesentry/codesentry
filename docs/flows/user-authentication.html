User Authentication (GitHub OAuth)

Service: api-service · Files: routes/auth.js, middleware/auth.js, services/githubUserAuth.js, utils/encryption.js

Mitig8it authenticates dashboard users with the GitHub OAuth authorization-code flow. GitHub performs the actual user authentication (credentials and 2FA); api-service exchanges the resulting authorization code for a GitHub access token, reads the user's identity, stores the tokens encrypted, and issues its own session JWT.

Ownership. This flow is handled entirely by api-service, the control plane. github-service handles a separate concern: GitHub App authentication (installation tokens for acting on repositories). analysis-service has no authentication role. In short: api-service authenticates users; github-service authenticates the app.
Channel model. The front channel travels through the browser and carries only public values (client_id, scope, redirect_uri, state). The back channel is a direct api-service → GitHub call and is the only place the client_secret is used. Redirects move the browser; the server makes direct API calls.

Request flow

B = browser · API = api-service · GH = GitHub

# Hop HTTP verb & URL Service · file Description Notes
1 B → API GET /auth/github api-service · routes/auth.js User clicks "Login with GitHub". The server builds a signed state value and returns a 302 redirect. Top-level browser navigation, not an AJAX request; the browser must follow the redirect.
2 API → B 302 Location: github.com/login/oauth/authorize?client_id&scope=read:user,user:email&redirect_uri&state api-service · routes/auth.js → createOAuthState() The redirect hands the browser GitHub's authorize URL. Response body is empty. Carries client_id (public) only, never the secret. state is an HMAC-SHA256 value signed with JWT_SECRET, used for CSRF protection. It is unrelated to the webhook signature.
3 B → GH GET github.com/login/oauth/authorize?... GitHub (external) GitHub validates client_id and redirect_uri, authenticates the user (login + 2FA), and shows the consent screen. User authentication happens here, on GitHub. api-service never receives credentials. state is opaque to GitHub and is echoed back unchanged.
4 GH → B 302 Location: /auth/github/callback?code&state GitHub (external) After the user authorizes, GitHub issues a single-use authorization code and redirects the browser back to the callback. The browser makes the next request, not GitHub. The redirect carries a code, but no user identity yet.
5 B → API GET /auth/github/callback?code&state api-service · routes/auth.js The callback receives the code and state. The code grants nothing on its own; it must be redeemed with the client secret.
6 API (internal) n/a api-service · routes/auth.js → isValidOAuthState() Verify state before doing anything else: recompute the HMAC, compare with timingSafeEqual, and check the 10-minute TTL. Runs before the code is redeemed. timingSafeEqual is a constant-time comparison, which prevents timing attacks against the signature.
7 API → GH POST github.com/login/oauth/access_token · body {client_id, client_secret, code} api-service · routes/auth.js Back-channel exchange: redeem the code for an access_token (and refresh_token / expires_in when present). The client_secret is used only here, server-to-server. The browser never sees it.
8 API → GH GET api.github.com/user · Authorization: Bearer <token> api-service · routes/auth.js Fetch the user's identity: { id, login, email, avatar_url, name }. Username (login) and email are obtained here, via a separate API call, not from the redirect.
9 API → GH GET api.github.com/user/emails api-service · routes/auth.js Only if /user returns a null email (private): select the primary verified address. If that also fails, synthesize id+login@users.noreply.github.com. Ensures the flow does not break when a user hides their email.
10 API → Postgres INSERT INTO users ... ON CONFLICT (github_id) DO UPDATE api-service · routes/auth.js + utils/encryption.js Encrypt the access and refresh tokens (AES-256-GCM), upsert the user, and return the internal id. Tokens are stored encrypted at rest, never in plaintext.
11 API → B Set-Cookie: __session=<JWT> · 302 → /dashboard api-service · routes/auth.js Sign a session JWT {user_id, github_id, github_username} (JWT_SECRET, 7-day expiry) and set it as the __session cookie. The session is the service's own JWT, not the GitHub token. The cookie is httpOnly and secure, so client-side JavaScript cannot read it and the GitHub token never reaches the browser.
12 B → API Any protected route · Cookie: __session api-service · middleware/auth.js → authenticateToken Each subsequent request is authenticated by verifying the JWT (jwt.verify) and attaching req.user. Missing or invalid token returns 401.

Design and security notes

  • Session token. api-service issues its own JWT rather than reusing the GitHub access token as the session. This decouples session lifetime, payload, and revocation from GitHub, and keeps the GitHub token off the browser.
  • CSRF state. The state value is {nonce, ts} (base64url) with an appended HMAC signature. It is signed and time-limited (10 minutes) rather than stored server-side, so it remains valid even when the callback is handled by a different Cloud Run instance than the one that started the flow.
  • State vs. webhook signature. Both use HMAC-SHA256, but they are separate mechanisms. The OAuth state is signed by api-service with JWT_SECRET for CSRF protection. The webhook signature is produced by GitHub with GITHUB_WEBHOOK_SECRET to prove payload integrity, and is verified in a different request.
  • Constant-time comparison. The state signature is compared with crypto.timingSafeEqual so the response time does not reveal how much of a guessed signature was correct.
  • Encryption at rest. Access and refresh tokens are encrypted with AES-256-GCM (random IV, authentication tag) using ENCRYPTION_KEY before being written to the database.
  • Token refresh. services/githubUserAuth.js stores the refresh token (also encrypted) and exchanges it for a fresh access token via refreshGithubAccessToken, using a 60-second expiry leeway, so users are not forced to re-authenticate when a token expires.

Resources

Database: users table

github_id, github_username, github_email, avatar_url, name, encrypted github_token and github_refresh_token, and the token expiry columns.

Environment / secrets

  • GITHUB_CLIENT_ID, GITHUB_CLIENT_SECRET: OAuth application credentials.
  • JWT_SECRET: signs the session JWT and the OAuth state.
  • ENCRYPTION_KEY: 32-byte key for AES-256-GCM token encryption.

Cookie

__session: the httpOnly, secure session JWT (7-day expiry).
